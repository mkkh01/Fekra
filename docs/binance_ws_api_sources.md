# Binance Spot WebSocket API — مصدر التحقق

المصدر الرسمي المقروء في 27 أغسطس 2026:

- https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/web-socket-api.md

## العقد المستخدم

الـendpoint العام الرسمي هو `wss://ws-api.binance.com:443/ws-api/v3`، والمنفذ 9443 بديل موثق. الطلبات ترسل كإطارات نصية JSON، وكل طلب يجب أن يحتوي `id` و`method`، و`params` اختيارية. الاستجابة تعيد نفس `id` و`status` و`result` عند النجاح أو `error` عند الفشل.

الطرق العامة التي تحققنا منها:

| الحاجة | method | الطلب/النتيجة | الوزن الرسمي |
|---|---|---|---:|
| وقت خادم Binance | `time` | `{"id":"...","method":"time"}`، والنتيجة تحتوي `serverTime` | 1 |
| قواعد التداول والرموز | `exchangeInfo` | يمكن إرسال `symbols` لعدة رموز أو بدون parameters؛ النتيجة تحتوي `symbols` و`serverTime` | 20 |
| الشموع التاريخية | `klines` | `symbol`, `interval`, `startTime`, `endTime`, `limit`، والنتيجة مصفوفة Kline | 2 |
| أفضل Bid/Ask | `ticker.book` | `symbol` أو `symbols`، والنتيجة كائن أو مصفوفة تحتوي `symbol`, `bidPrice`, `bidQty`, `askPrice`, `askQty` | 2 لرمز، 4 لـ`symbols` |

الوثيقة تذكر أن `exchangeInfo` بدون parameters يعرض الرموز ذات صلاحيات `SPOT`, `MARGIN`, `LEVERAGED`، وأن استخدام `permissions` صراحةً مطلوب إذا كان الهدف قائمة كل الرموز النشطة. المشروع يستخدم قائمة رموز محددة، لذلك لا يُقبل القرار إلا بعد العثور على الرمز المطلوب وقواعده في استجابة حديثة.

## حدود الأمان التشغيلي

الوثيقة الرسمية تشرح أن HTTP/WebSocket API يستخدم status `418` عند الحظر التلقائي بعد خرق متكرر للحدود، و`429` عند تجاوز معدل الطلب، وأن تكرار الإرسال بعد `429` قد يؤدي إلى حظر IP. لذلك يبقى REST fallback محدودًا عبر circuit breaker، ولا توجد إعادة محاولات غير محدودة.

اتصال WebSocket API صالح لمدة 24 ساعة، ويرسل الخادم ping دوريًا؛ التنفيذ يحتفظ باتصال مشترك واحد ويُسلسل الطلبات عبر lock، ويغلقه ويعيد إنشاءه عند الانقطاع أو انتهاء المهلة. هذا يمنع عاصفة الاتصالات المتزامنة أثناء تحميل التاريخ، مع الالتزام بإعادة الاتصال قبل حد 24 ساعة عند الحاجة.

## سياسة البيانات

هذه الوسيلة ليست cache بديلًا: نتيجة WebSocket API تُسجل وقت استلامها الحالي، وأي فشل في REST وWebSocket معًا يرفع خطأ ولا يعيد القيمة السابقة لقبول قرار جديد. أما تدفقات `@kline` و`@ticker` و`@bookTicker` فتُقبل فقط عبر نافذة freshness الحالية في طبقة القرار.
